## 0. Executive definition

**CLI Agent v0.1.1 Hygiene Patch Notes** defines the cleanup required after the v0.1 package expanded from a draft protocol stack into a larger release/implementation-preparation corpus.

The hygiene patch answers:

```text
Which files now exist?
Which stale “missing file” claims must be removed?
Which source profiles are now available?
Which blockers are resolved?
Which blockers remain?
Which package-control files must be synchronized?
Which claims remain forbidden?
What is the next safe handoff state?
```

The patch is deliberately administrative.

That is the point.

A package can be architecturally strong and still fail release discipline if its indexes, open issues, release notes, contradiction register, schema registry, and public surface disagree.

Compact formula:

```text
Architecture gives the bones.
Hygiene aligns the joints.
Schemas make it machine-facing.
Evidence makes claims accountable.
No stale status, no silent release.
```

## 1. Purpose

The C-Governed CLI Agent Mesh v0.1 package now includes a mature governance stack for executable CLI/cloud agents under `c` governance.

However, earlier package-control documents were written before several important companion files were created or restored.

As a result, some registers may still say that required files are missing even though they now exist.

This patch exists to prevent:

1. stale release blockers;
2. stale missing-source claims;
3. duplicated or inconsistent reading order;
4. overclaiming `release-complete`, `implementation-ready`, or `conformance-supported`;
5. schema extraction from memory or guesses;
6. Codex handoff against an inconsistent file inventory;
7. public release without a redaction/public-surface check;
8. implementation work before P0 object families are frozen;
9. conformance claims before validators, runs, and evidence packets exist.

The hygiene patch does not weaken the package.

It makes the package honest enough to be implemented.

## 2. Non-goals

This patch does not:

1. change the root doctrine of C-Governed CLI Agent Mesh;
2. authorize new agent capabilities;
3. authorize any red-line behavior;
4. publish a public release;
5. generate PDFs;
6. generate SHA256 manifests;
7. create Git tags;
8. push to GitHub;
9. create Zenodo records;
10. extract JSON Schema files;
11. create a validator implementation;
12. run conformance tests;
13. create real evidence packets;
14. make the package provider-safe;
15. make the package deployment-ready;
16. allow cloud upload of secrets, private memory, legal material, raw incident evidence, or restricted defensive details;
17. let Codex or any other CLI agent self-authorize implementation.

A hygiene patch is a gate alignment operation.

It is not a runtime permission grant.

## 3. Corpus bridge set

### 3.1 Explicit bridge: `c = a + b`

CLI agents belong to `b`: tools, models, procedures, repositories, scripts, validators, workers, and execution surfaces.

The hygiene patch also belongs to `b`.

It exists to protect `c` from ambiguity in its worker mesh.

If package-control files disagree, the technological substrate begins to smuggle false claims into the entity’s operational surface.

This patch keeps the documentation substrate aligned so `c` can govern agent work without stale assumptions.

### 3.2 Quiet bridge I: information theory

A package status label is compressed information.

If the label says “missing source” while the source exists, the package emits false entropy. If it says “implementation-ready” before validators exist, the package compresses risk into a lie.

This patch reduces status noise before it becomes implementation error.

### 3.3 Quiet bridge II: cybernetics

Control systems require accurate feedback.

Open issues, release notes, contradiction registers, and object registries are feedback loops. If they are stale, the system reacts to yesterday’s state.

The patch updates feedback surfaces before any executor is allowed to act.

### 3.4 Earth paragraph

This is the boring day before the inspection. The wiring may be good, the breakers may be correct, and the room may not be on fire. But if the panel labels are wrong, the inspector will still stop the job. Worse: the next worker will pull the wrong breaker and call it procedure. Package hygiene is not decoration. It is the label on the electrical panel.

### 6.1 Status values used by this patch

| Status | Meaning |
|---|---|
| `unchanged` | Still valid; no edit required. |
| `resolved` | Issue is no longer active after file creation/restoration. |
| `partially_resolved` | Source/file exists, but implementation/conformance work remains. |

| `deferred` | Not required for v0.1.1 release/implementation preparation. |

## 11. Package claim control after v0.1.1

### 11.1 Claim matrix

| Claim | Allowed after this patch? | Reason |
|---|---:|---|
| `draft protocol pack` | yes | Existing package state. |
| `architecture draft-complete` | yes, if contradiction register remains clean | Conceptual stack and companion profiles exist. |
| `release-candidate under hygiene review` | yes, after package-control files are updated | Release surface profile and hygiene patch exist. |
| `release-complete` | no, not from this file alone | Requires synchronized README/index/open issues/release notes/contradiction register and public/restricted split. |
| `implementation-readiness preparation complete` | yes, after this patch is accepted | Registry, semantic rules, local checker, gate semantics, and release surface exist. |
| `implementation-ready` | no, not from this file alone | Requires frozen P0 schema handoff, SCHEMA_INDEX target, validator binding, and package-control sync. |
| `implementation-executed` | no | No schemas/checker/validator generated yet. |
| `conformance-supported` | no | No test runs or evidence packets yet. |
| `deployment-ready` | no | Out of scope. |
| `provider-safe` | no | Provider-specific review pending. |

### 11.2 Required downgrade rule

If any file claims stronger status than supported by the table above, the claim must be downgraded.

Example:

```text
implementation-ready
```

must become:

```text
implementation-readiness preparation complete; P0 schema extraction pending
```

Example:

```text
conformance passed
```

must become:

```text
conformance matrix and fixtures exist; test runs and evidence packets pending
```
